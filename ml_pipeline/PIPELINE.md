## Предлагаемая задача для обучения

**Единица и момент.** Одно первое клиентское сообщение на входе в чат магазина Softline. Модель выбирает первый маршрут до поиска товаров. Вход для первой версии — только текст клиента на этот момент. Номер обращения, имя файла, архивная метка, ответы менеджера, резюме и дальнейший исход исключаются. Если первое сообщение нельзя выделить уверенно, строка архива пригодна как источник тем, но не как размеченная реплика клиента.

**Цель.** Обучить компактный маршрутизатор. Редакцию, цену, наличие, совместимость и достаточность источников продолжает проверять агент по каталогу и документации. Claude Haiku остаётся генератором ответа. Архивные темы используются для отбора примеров и не считаются целевым классом.

| Метка | Ожидаемый первый шаг |
| --- | --- |
| `find_named_product` | Клиент указал продукт и хочет выбрать позицию, редакцию или вариант лицензии. |
| `recommend_by_need` | Клиент описал задачу, но подходящий продукт не назвал. Начать сбор требований. |
| `answer_product_question` | Клиент спрашивает конкретный факт о продукте: цену, наличие, характеристики или условия лицензии. Проверить источник. |
| `handoff` | Явный запрос менеджера или индивидуального решения, например особой скидки. |
| `clarify` | По имеющемуся сообщению нельзя надёжно выбрать ветку. Уточнить цель. |

Если есть явный запрос менеджера, он имеет приоритет. Проверка товара может привести к уточнению или передаче после маршрутизации. `handoff` на обучении обозначает вход, где передача нужна сразу, а не любое обращение, которое потом дошло до менеджера.

**Базовая проверка.** Сравнить предсказание самого частого класса и TF-IDF + логистическую регрессию с текущей маршрутизацией на Haiku или правилах. Основная метрика — macro-F1 по подтверждённым классам. Дополнительно — полнота по `handoff`, матрица ошибок, число примеров на класс и доля сообщений, на которых пришлось уточнять маршрут. Для проверки качества продукта отдельно считаем Hit@5 по каталогу и нарушения обязательных ограничений, когда появится разметка допустимых SKU.

**Следующий этап после согласования.** Выбрать примеры с проверяемым входом клиента, разметить маршруты и отдельно отметить синтетические реплики для редких веток. Проверить близкие дубли и разнести по группам целых обращений. Если появятся даты разговоров, использовать хронологическое разделение с сохранением групп. После разделения собрать предобработку, не подбирая ничего по финальному тесту. При недостаточном покрытии классов сообщить это до обучения и продолжить с проверяемым поиском и Haiku.

**Отдельный поток для агента.** Включить адаптер реального фида и поиск по SKU/семействам. Доля предложений с указанной версией около 1,6%, архитектурой или платформой — менее 1%. Пустое поле трактуем как неизвестное и при необходимости проверяем по карточке или документации. Каталог — источник проверяемых данных, не корпус для обучения генерации цен и наличия.

## Подготовленные данные и ограничения

- Сбрасываем служебные заголовки темы и страницы магазина. 21 запись без распознаваемого заголовка страницы оставлена в архиве; 202 не прошли ограничение по границе и длине первого вопроса; 33 содержали признаки контактных данных, идентифицирующий контекст или маркеры нескольких реплик. Результат отбора — 239 кандидатов. Префикс до первого `?` является только предположением о границе, поэтому обучение использует лишь фрагменты, проверенные вручную.
- В файле решений хранятся позиции 55 проверенных строк и контрольная сумма исходного архива. Из этих 55 явных дубликатов и почти одинаковых формулировок по фиксированному текстовому порогу не найдено. По одной реплике на обращение, даты сообщений отсутствуют. Выборка стратифицирована по размеченному маршруту, seed `26112026`. Параллельные обращения одного клиента без группового идентификатора отличить нельзя.
- По маршрутам в архивных фрагментах: 11 «товар назван», 5 «подбор по задаче», 26 «факт о товаре», 2 «передача менеджеру», 11 «уточнение». В каждую контрольную часть попало по одному примеру подбора по задаче и ни одного примера передачи менеджеру. Результаты пригодны для диагностики прототипа, но недостаточны для оценки в бою. Полноту `handoff` на реальных данных здесь оценить нельзя.
- Используем 35 архивных и 30 отдельно созданных синтетических реплик для обучения. Валидация и замороженная проверка содержат по 10 архивных фрагментов. Синтетика не попала ни в одну из контрольных частей. Размеченные тексты и индекс хранятся в игнорируемой `ml_pipeline/.local/`.
- Ноутбук `PYTHONPATH=. marimo edit ml_pipeline/02_prep.py` читает агрегаты. Для первой подготовки используется `SOFTLINE_PREP_MODE=prepare python -m ml_pipeline.02_prep`; повторная подготовка с тем же путём защищена от перезаписи замороженного набора. Требуется также `scikit-learn`.
- Локальный индекс реального фида строится командой `python -m aisupport_ml.commerce.catalog <фид.xml> <новый-индекс.sqlite>`. Проверены 136 040 предложений, 44 601 доступное и позиции MDaemon `19579`, `19590`, `19601` для 50 пользователей. Совпадение `MDaemon Standard` по названию не подтверждает редакцию. Адаптер доступен отдельно от чата, подключение к `CommerceAgent` и проверка ответов на живом каталоге остаются следующими шагами.

Model rationale:
- traits: 5 классов, 65 обучающих реплик (35 архивных, 30 синтетических), 10 архивных валидационных, 10 архивных отложенных; нет дат, один фрагмент на обращение; на валидации нет `handoff`.
- baseline: самый частый класс из обучения и TF-IDF по словам (1–2 слова) + логистическая регрессия.
- candidates: TF-IDF по словам и символам (3–5 символов) + логистическая регрессия с регуляризацией; короткое сравнение с эвристическим маршрутизатором.
- ruled out: дообучение Haiku и обучение трансформера на десятках примеров; настройка порогов по финальному набору; запуск маршрутизатора в чате по результатам такого малого набора.
- metric: macro-F1 на классах с поддержкой в архивной валидации плюс поддержка по каждому классу, матрица ошибок и отдельная полнота `handoff` после появления размеченных контрольных примеров.

## Валидация маршрутизатора · 26 ноября 2026

Для отбора использовали 10 архивных реплик. Всего четыре представленных маршрута, пять запросов фактов, два запроса по названным продуктам, два уточнения и один запрос подбора. Сценариев передачи менеджеру нет. Macro-F1 усредняется по представленным классам. Неверные прогнозы передачи по-прежнему учитываются как ошибки своих фактических классов.

| Вариант | Macro-F1 | Верных маршрутов |
| --- | ---: | ---: |
| Самый частый класс | 0,167 | 5/10 |
| Простые правила | 0,575 | 8/10 |
| TF-IDF по словам + логистическая регрессия | 0,525 | 5/10 |
| Слова и символы, только архив, C=1 | 0,167 | 5/10 |
| Слова и символы, архив и синтетика, C=0,3 | 0,317 | 4/10 |
| Слова и символы, архив и синтетика, C=1 | 0,250 | 4/10 |
| Слова и символы, архив и синтетика, C=3 | 0,250 | 4/10 |

При одинаковых признаках и C синтетика подняла Macro-F1 с 0,167 до 0,250, хотя число правильно назначенных маршрутов уменьшилось с пяти до четырёх. Это диагностический результат одного маленького набора. Добавление символьных признаков не обошло TF-IDF по словам. Выбран лучший обученный кандидат `words`, локально сохранён для проверки и воспроизводит прогнозы после загрузки.

Правила пока сильнее обученной модели. У кандидата `words` оба валидационных запроса по названному продукту перешли в ветку фактов о товаре, ещё два запроса ошибочно ушли в `handoff`. Веб-чат пока оставляем на исходном решении. После согласования можно разобрать ошибки и один раз оценить замороженный набор с тем же кандидатом и заранее зафиксированным сравнением. `test_touches = 0`.

## Исправление маршрутов и план финальной проверки

На валидации увидели три причины. Слабое предсказание передачи перехватывало вопросы о наличии и неясную просьбу о спецификации. Признаки слов не отличали выбор редакции от вопросов о фактах. Базовые правила путали список требуемых функций с названием программы. Пиковые вероятности модели на всех десяти фрагментах оставались ниже 0,50.

Версия `catalog_guard_v2` ставит ручную передачу только по явной просьбе о человеке или индивидуальных условиях. Выбор версии или лицензии проверяет упомянутое название по заголовкам реального каталога. Этот сигнал не подтверждает редакцию, цену или наличие. Слабые предсказания оставляют маршрут на уточнении; модель может предложить только подбор по задаче при оценке от 0,55. Это фиксированный порог для эксперимента, не откалиброванная вероятность.

Диагностика на той же валидации: `catalog_guard_v2` 10/10, исходные правила 8/10, TF-IDF 5/10. Это проверка правок на знакомых данных. Отдельные синтетические регрессии закрывают приоритет явного выбора версии, наличие, требование уточнения, явную просьбу о менеджере, отказ от перевода и техническое употребление слова «оператор».

До открытия отложенных данных фиксируем код и каталог, обученный артефакт, отпечаток набора и порядок трёх вариантов. Основная метрика финального прогона — Macro-F1 по классам с положительной поддержкой у `catalog_guard_v2`. Одновременно считаем те же значения для двух замороженных вариантов сравнения. Один вызов проверки, без корректировки порогов по итоговому набору. Команды и агрегаты доступны в `ml_pipeline/04_eval.py`.

Список хешей и отпечаток набора лежат в `.local/route-fix-v2/frozen_comparison.json`. Для просмотра результатов: `PYTHONPATH=. marimo edit ml_pipeline/04_eval.py`. По умолчанию ноутбук читает готовый отчёт. Повтор открытия набора для расчёта запрещён.

## Проверка следующей версии

В следующем наборе собрать независимые первые клиентские реплики, уделив внимание выбору версии, подбору по задаче и явной просьбе о менеджере. Для каждого кейса сохранять источник, ожидаемый маршрут и при необходимости проверяемый товарный ориентир. В новом протоколе заранее согласовать разбиение, набор допустимых метрик по каждому классу и минимальную поддержку классов. При отсутствии живых примеров важной ветки результат помечать как диагностический.

В будущей теневой проверке без влияния на ответы сравнивать ошибки по маршрутам, долю уточнений и ложных передач, покрытие названий в каталоге и дрейф по версиям фида. Решение о подключении принимать по независимой проверке в сравнении с текущей маршрутизацией. При росте ошибок в критическом классе или значимом изменении состава обращений сначала собрать новую разметку и одобрить новый цикл оценки. Следующее обучение и проверка не используют закрытый набор этой итерации для подбора параметров.
